# Windows/macOS 验证说明：1.0.4

1.0.4 包含 Windows 文件锁和跨平台在线“检查连接”冲突修复。此前测试包的相关问题场景已通过用户验证，以下步骤可用于安装后复核。

## 修复范围

保存 Octo 通道配置时，宿主会执行一次启动/停止探测。旧版在打开 SQLite 状态库时无条件导入 Unix 专用 `fcntl`，因此 Windows 可以安装插件，但保存探测失败。

本版 Windows 使用 Python 标准库 `msvcrt` 的非阻塞字节锁，Linux/macOS 继续使用 `flock`，不增加依赖。相同状态库仍禁止两个消费者同时打开；关闭、初始化失败和进程退出都会释放文件句柄及锁。状态库格式未改变。

后续复现确认：即使通道已经连接正常，宿主点击“检查连接”仍会用相同通道 ID 创建临时实例，旧流程也会打开同一状态库，因此 Windows/macOS 都会出现 `Octo state already owned by another process`。本版通过 gateway 的入队注册状态区分探测与运行：探测只验证 API 凭证/注册信息，不创建状态库、第二个 WS 连接或消息消费者；在线通道继续持有原锁。

同时修复了 Windows 只读诊断的文件 URI，并增加 Windows CI 配置。本地 macOS 上的 Windows 适配器模拟测试不能代替 Windows 实机验证；用户验收与仓库 Actions 中的 Windows 自动化结果应分别核对。

## 安装

1. 保留原 Bot Token、API URL 与现有状态目录；测试前停止旧 Octo 通道。
2. 在 Octop 管理页面上传 `octop-channel-octo-1.0.4.zip`，覆盖同 ID 插件。
3. 重新加载插件或重启 Octop，确认插件版本为 `1.0.4`，避免进程继续使用旧模块。
4. 保持原 Token/API URL，打开 Octo 通道配置并保存。

## 需要反馈的验证结果

- **在线检查连接**：保持 Octo 通道启用并显示连接正常，在设置页连续点击“检查连接”三次；均不应出现状态锁占用，当前通道应继续保持在线。此用例也适用于 macOS。
- **配置保存**：保存成功，不再出现 `No module named 'fcntl'`；停止通道后再次保存/启动也正常。
- **收发消息**：私聊一条文本；群聊直接 @机器人一条文本，确认能收到回复。
- **重启恢复**：重启 Octop 后能再次启动通道并收发消息，已有状态无需删除。
- **异常占用**：真正启动第二个相同 Bot/状态库的消费者仍会被拒绝；不要删除锁文件绕过保护。1.0.4 的在线“检查连接”不应触发此错误。

如仍报错，请提供 Windows 版本、Python 版本、Octop 版本，以及从点击保存到失败期间的相关错误堆栈。日志中的 Token 和消息正文应先移除。

Windows 状态目录由当前账户的用户目录或 `OCTOP_HOME` 决定；使用自定义目录时应有写入权限。权限继承目录 ACL，不以 Unix 的 0600/0700 模式位作为 Windows 权限保证。
